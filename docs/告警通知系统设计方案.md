# 告警通知系统设计方案

> 目标：把 CyberGuard 从「监控展示」推进到「监控 + 响应」，
> 补上安全运营闭环中最关键的一环 —— **告警触达**。
>
> 本文档为设计方案（尚未实现）。请先评审，确认后再落地。

---

## 一、为什么值得做

当前系统已经具备：真实检测规则 → 告警落库 → 可视化 → 权限分级 → 封禁生效。
**唯一缺的是"当没有人盯着屏幕时，怎么知道出事了"。**

真实 SOC 的告警链路是：

```
检测 → 告警 → 分级 → 通知值班人 → 处置 → 复盘
                      ↑
                当前缺失这一环
```

补上它有两个直接收益：

1. **能力闭环**：项目从"可视化作品"升级为"可响应的安全运营系统"
2. **天然的技术亮点**：通知系统涉及异步投递、限流去重、渠道抽象、失败降级 ——
   这些都是真实工程问题，不是"调个 API"

## 二、渠道选型：哪些能真做，哪些不能

| 渠道 | 可行性 | 成本 | 门槛 | 建议 |
|---|---|---|---|---|
| **钉钉群机器人** | ✅ | 免费 | 群设置里点一下即得 webhook | **主力渠道** |
| **企业微信群机器人** | ✅ | 免费 | 同上，配置更简单 | **主力渠道** |
| **邮件 SMTP** | ✅ | 免费 | 自己的邮箱授权码 | 推荐 |
| **浏览器桌面通知** | ✅ | 免费 | 用户授权 | 推荐 |
| **Server酱 / PushPlus** | ✅ | 免费额度 | 扫码绑定微信 | 可选 |
| **短信** | ⚠️ | ¥0.045/条 | 见下 | **仅做适配器预留** |

### 短信的真实门槛（不是技术问题，是资质问题）

| 门槛 | 说明 |
|---|---|
| **签名资质** | 需企业资质，或个人实名 + 应用备案，签名需审核 |
| **模板报备** | 短信内容必须预审为固定模板（约 1~2 个工作日），**不能自由拼接** |
| **按条计费** | 约 ¥0.045/条，需预充值 |

**结论**：除非已申请好短信服务，否则现场真发短信不现实。

**我们采取的做法（重要）**：
把短信实现为一个**完整可用的适配器接口**（代码、配置、界面齐备），
但界面上**如实标注其状态为「待配置资质」**，演示环境使用 Mock 发送器。

> 答辩话术：「通知系统采用可插拔渠道架构，已实现钉钉/企微/邮件/浏览器四类真实渠道；
> 短信渠道已完成适配器对接代码，但因国内短信需要企业签名与模板报备资质，
> 演示环境标记为『待配置』—— **我们没有把未配置的渠道伪装成可用**。」

这个"诚实的预留"比"假装能发短信"得分高，且证明团队了解生产环境门槛。

## 三、系统架构

```
                       ┌──────────────────────────┐
    告警产生 ─────────► │      通知规则引擎         │
  （DDoS 沙箱告警       │                          │
   + 登录检测告警）      │  ① 渠道是否启用           │
                       │  ② 风险等级是否达阈值      │
                       │  ③ 是否处于静默时段        │
                       │  ④ 去重（同源+同类型）     │
                       │  ⑤ 限流（滑动窗口）        │
                       │  ⑥ 聚合（同波合并）        │
                       └────────────┬─────────────┘
                                    │ 通过的告警
                       ┌────────────▼─────────────┐
                       │       渠道分发器          │
                       │  （异步、超时、失败隔离）   │
                       └────────────┬─────────────┘
          ┌──────────┬──────────────┼──────────────┬──────────┐
          ▼          ▼              ▼              ▼          ▼
       钉钉      企业微信          邮件        浏览器通知    短信
     (webhook)  (webhook)       (SMTP)     (Notifications) (适配器预留)
          │          │              │              │          │
          └──────────┴──────────────┼──────────────┴──────────┘
                                    ▼
                       ┌──────────────────────────┐
                       │     通知投递日志          │
                       │ （落库，页面可查投递结果） │
                       └──────────────────────────┘
```

### 核心设计原则

| 原则 | 理由 |
|---|---|
| **通知决策在服务端** | 前端决定发不发 → 刷新页面/多开标签页就会重复推送 |
| **投递异步化** | webhook 超时 5 秒不能阻塞告警生成主流程 |
| **失败必须隔离** | 任一渠道失败不影响其它渠道，也不影响主业务 |
| **全量留痕** | 每次投递（成功/失败/被限流）都落库，可追溯 |
| **配置与密钥分离** | webhook URL 含密钥，不明文回显给前端 |

## 四、模块划分

### 4.1 新增文件

```
utils/notifier.py              # 通知核心：渠道抽象 + 规则引擎 + 分发器
utils/channels/__init__.py
utils/channels/webhook.py      # 钉钉 / 企业微信（同一套 webhook 逻辑）
utils/channels/email.py        # SMTP
utils/channels/sms.py          # 短信适配器（预留，含 Mock 发送器）
templates/notify.html          # 通知配置与投递记录页（仅管理员）
```

### 4.2 渠道抽象接口

```python
class NotificationChannel:
    """通知渠道抽象基类。

    新增渠道只需实现 send()，并在 CHANNEL_REGISTRY 注册 —— 
    规则引擎与分发器无需任何改动。
    """
    key: str            # 渠道标识，如 'dingtalk'
    name: str           # 展示名，如 '钉钉群机器人'
    requires: list      # 必需配置项，用于界面提示与校验
    tier: str           # 'real'（真实可用）/ 'reserved'（待配置资质）

    def is_configured(self) -> bool: ...
    def send(self, alert: dict, rendered: str) -> tuple[bool, str]:
        """返回 (成功与否, 说明)。实现内部必须自行处理超时与异常。"""
```

**渠道注册表**：

| key | name | tier | 必需配置 |
|---|---|---|---|
| `dingtalk` | 钉钉群机器人 | real | webhook URL（+ 可选加签密钥） |
| `wecom` | 企业微信群机器人 | real | webhook URL |
| `email` | 邮件 SMTP | real | SMTP 主机/端口/账号/授权码/收件人 |
| `browser` | 浏览器桌面通知 | real | 无（前端授权） |
| `sms` | 短信 | **reserved** | 服务商 AccessKey / 签名 / 模板 ID |

### 4.3 规则引擎（顺序即优先级）

```
① 渠道启用检查          —— 未启用直接跳过（零成本）
② 风险等级阈值          —— 如"仅高危"或"中危以上"
③ 静默时段检查          —— 非工作时段仅放行高危
④ 去重                  —— 同 IP + 同告警类型，N 分钟内只通知一次
⑤ 限流                  —— 渠道级滑动窗口，超限则合并/丢弃并记录
⑥ 聚合（可选）          —— 同一波攻击的多条告警合并为一条摘要
```

**顺序设计理由**：先做廉价判断（开关、阈值），再做需要查库的判断（去重、限流），
避免为注定要被丢弃的告警做数据库查询。

## 五、数据结构

### 5.1 配置表 `notify_config`

采用 key-value 结构（而非宽表），便于扩展渠道而无需改表：

| key | 说明 | 是否敏感 |
|---|---|---|
| `channel.<key>.enabled` | 渠道开关 | 否 |
| `channel.<key>.<field>` | 各渠道配置项 | **是**（webhook URL / 授权码） |
| `rule.min_risk` | 最低通知风险等级 | 否 |
| `rule.dedup_minutes` | 去重窗口（默认 5） | 否 |
| `rule.rate_limit_per_5min` | 限流阈值（默认 3） | 否 |
| `rule.quiet_hours` | 静默时段（如 `22:00-08:00`） | 否 |
| `rule.quiet_min_risk` | 静默时段内仍放行的等级（默认 `高危`） | 否 |

> **敏感项处理**：界面回显时只显示掩码（如 `https://oapi.dingtalk.com/robot/send?access_token=***a1b2`），
> 完整值仅存库、仅服务端使用。同时支持从环境变量读取（优先级高于库）。

### 5.2 投递日志表 `notify_log`

| 字段 | 说明 |
|---|---|
| id | 主键 |
| created_at | 投递时间 |
| alert_id | 关联的告警（可空） |
| channel | 渠道标识 |
| alert_type / risk_level | 告警类型与等级（冗余存储便于统计） |
| target | 投递目标（**掩码后**，如群机器人名称） |
| status | `sent` / `failed` / `rate_limited` / `deduped` / `skipped_quiet` |
| detail | 失败原因或限流说明 |
| latency_ms | 投递耗时 |

**这张表是"可验证性"的基础**：页面能看到"哪条告警、通过哪个渠道、什么时候、成功与否"。

## 六、必须处理的四个坑

### 坑 1：告警风暴（最严重）

我们的攻击浪潮**突袭期速率是 70 个/分钟**。若每条告警都推送，
一分钟 70 条通知 —— **这在真实 SOC 里叫 alert fatigue（告警疲劳）**，
后果是值班人直接关掉通知，真正的高危告警反而被淹没。

**三层防护**：

| 层 | 手段 | 效果 |
|---|---|---|
| 去重 | 同 IP + 同类型 5 分钟内只发一次 | 把 70 条压到个位数 |
| 限流 | 每渠道每 5 分钟最多 3 条 | 硬上限 |
| 聚合 | 超限时合并为「另有 N 条告警」摘要 | 信息不丢失 |

**实测目标**：一次完整突袭期（约 1 分钟）产出的通知不超过 **3 条**。

### 坑 2：静默时段与休息权

非工作时间的告警推送涉及员工休息权，真实企业普遍设置静默时段。
本设计支持 `quiet_hours`，并在静默期内**仅放行高危及以上**。

> 这一点在说明书里值得单独写一句 —— 它体现的是"理解真实运维的伦理约束"，
> 而不只是"会调 API"。

### 坑 3：内容最小化（数据外发）

通知内容会经由**第三方服务器**（钉钉/企微/邮件服务商）传递。必须遵循最小必要原则：

**包含**：告警类型、风险等级、来源 IP、来源国家、峰值带宽、目标服务、时间、处置状态
**不包含**：完整日志、用户名、User-Agent、内网拓扑、其它告警的批量明文

### 坑 4：渠道失败降级

webhook 可能超时、SMTP 可能拒信、DNS 可能解析失败。

**要求**：异步 + 超时（5 秒）+ 异常隔离 + 失败落库。
**通知发送失败绝不能影响告警生成与主业务流程。**

## 八、安全与合规

| 项 | 措施 |
|---|---|
| **权限** | 通知页面与全部 API 仅管理员可访问（服务端强制） |
| **密钥保护** | webhook URL、SMTP 授权码不回显明文；支持环境变量注入 |
| **SSRF 防护** | webhook 目标**白名单校验**，仅允许 `oapi.dingtalk.com`、`qyapi.weixin.qq.com` 等已知域名 —— 防止被改造成内网探测工具 |
| **数据最小化** | 见坑 3 |
| **投递留痕** | 全部投递（含被限流/去重）落库，可审计 |
| **不做假发送** | 短信渠道标注真实状态，Mock 发送器在日志中明确标记 `MOCK` |

> **SSRF 防护值得单独强调**：一个"可配置 URL 并让服务端发起请求"的功能，
> 如果不做目标校验，就是标准的 SSRF 漏洞。我们的作品本身是安全主题，
> **不能在这个功能上留下一个真实的 SSRF**。这是答辩时可以主动讲的细节。

## 十、测试与可验证性

### 10.1 自动化测试用例

| 用例 | 断言 |
|---|---|
| 渠道未启用 | 不产生投递记录 |
| 低于风险阈值 | 状态为 `skipped` |
| 同一告警重复触发 | 第二次状态为 `deduped` |
| 突袭期 70 条告警 | 实际投递 ≤ 3 条，其余为 `rate_limited` |
| 静默时段 + 中危告警 | 状态为 `skipped_quiet` |
| 静默时段 + 高危告警 | 正常投递 |
| webhook 超时 | 状态为 `failed`，**主流程不受影响** |
| 非白名单 URL | 拒绝投递并记录原因（SSRF 防护） |
| 短信渠道 | 状态为 `reserved`，Mock 发送器标记 `MOCK` |

### 10.2 现场演示脚本（3 分钟）

1. 打开 `/notify` 页 → 展示渠道状态（含短信"待配置资质"的诚实标注）
2. 点击钉钉渠道「发送测试通知」→ **手机当场收到**
3. 进入 log 页 → 点「引燃一波攻击」
4. 观察：钉钉群收到**聚合后的一条**告警摘要（而非 70 条）
5. 打开投递记录 → 展示"70 条告警 → 1 条通知，其余 69 条被去重/限流"
6. 讲解三层防护与静默时段设计

**第 5 步是最有说服力的**：它把"告警疲劳"这个真实痛点变成了可视化的工程答案。
